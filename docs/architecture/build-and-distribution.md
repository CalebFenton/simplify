# Build and Distribution Architecture

This describes the public Simplify build, embedding boundary, artifact contents, and publication requirements.

## Toolchain and dependency resolution

- The wrapper uses Gradle **9.7.0**, with its distribution SHA-256 pinned. The wrapper JAR and both
  launch scripts are generated by that version.
- Kotlin **2.4.21** supports Gradle through 9.7.0 according to the
  [Kotlin compatibility table](https://kotlinlang.org/docs/gradle-configure-project.html).
  Newer Gradle releases are not selected merely because they exist.
- Every root subproject uses a **JDK 21 toolchain** and JVM 21 bytecode. Java compilation also sets
  `--release 21`. Building and running the applications requires JDK 21 or later; install JDK 21
  locally for the pinned build toolchain. There is no automatic JDK download plugin.
- Production dependencies resolve from Google Maven and Maven Central. `mavenLocal()` and retired
  JCenter resolution are removed, so a developer's unpublished local artifacts do not shadow releases.
- Versions are declared in `build.gradle` and module build files. No dependency lockfile, dependency
  checksum manifest, publication repository, or signing workflow is configured.
- The Gradle daemon has a 2 GiB maximum heap and 512 MiB maximum metaspace. The optional ProGuard
  task exhausted the default 512 MiB heap during whole-library analysis; worker JVMs have separate limits.

The root applies Kotlin/JVM, JaCoCo, and shared compilation/test settings. Each module declares its
library or application role. Kotlin files remain under the existing `src/*/java` directories.

## Modules and public library boundary

| Module | Role | Dependency on SmaliVM |
|---|---|---|
| `smalivm` | Kotlin execution engine, immutable snapshots, method editing, DEX/class infrastructure | Library owner |
| `simplify` | Kotlin optimizer and CLI | Production API; shared SmaliVM test output for fixture helpers |
| `demoapp` | Kotlin embedding example | Production API |
| `sdbg` | Kotlin interactive debugger | Production API and Baksmali rendering |

Google's maintained [Smali fork](https://github.com/google/smali) replaces the unmaintained original:

| Maven artifact | Version | Namespace |
|---|---|---|
| `com.android.tools.smali:smali-dexlib2` | 3.0.10 | `com.android.tools.smali.dexlib2` |
| `com.android.tools.smali:smali` | 3.0.10 | `com.android.tools.smali.smali` |
| `com.android.tools.smali:smali-baksmali` | 3.0.10 | `com.android.tools.smali.baksmali` |
| `com.android.tools.smali:smali-util` | 3.0.10 | `com.android.tools.smali.util` |

All four remain exported through SmaliVM's `api` configuration. Public signatures exposing DEX types
now use the new namespace. This is an intentional API cutover, not a compatibility layer.

Other direct dependencies include Guava, Commons Lang/CLI, ASM, Kotlin immutable collections,
SLF4J, Picocli/JLine, and Jansi. Tests use JUnit 6 with an explicit Platform launcher, Mockito, and
MockK. The JUnit 4 runner bridge is removed. Android Base64 is compiled from pinned AOSP
`android-7.1.1_r1` source, with its original Apache header and provenance in `THIRD_PARTY_NOTICES`.

`simplify/ObfuscatedApp` is a **separate historical Android fixture build**, not a root subproject.
Its AGP/Gradle/SDK versions are not modernized by the host build. The checked-in APK remains an input;
root `build` does not rebuild, sign, install, or instrument that fixture.

## Logging ownership

SmaliVM depends only on the SLF4J API in production. It packages neither a logging provider nor a
root `logback.xml`, so it cannot impose configuration on embedding applications.

- Simplify and SDBG each own one `logback.xml` and use Logback 1.6.6 with SLF4J 2.0.20.
- The demo selects `slf4j-nop` and has no Logback configuration.
- SmaliVM's `logback-test.xml` is test-only. Simplify consumes that same test resource through the
  existing shared test-output dependency; it does not add a second configuration or an unused file appender.
- Application log-level controls intentionally use Logback. They are not a provider-neutral embedding API.

See [startup logging ownership](startup-and-policy.md#packaged-logging-ownership).

## Artifacts and tasks

| Task | Output / scope |
|---|---|
| `build` | All four modules' ordinary JARs and tests; application TAR/ZIP distributions |
| `:simplify:fatJar` | `simplify/build/libs/simplify.jar` |
| `:demoapp:fatJar` | `demoapp/build/libs/demoapp.jar` |
| `:sdbg:fatJar` | `sdbg/build/libs/sdbg.jar` |
| `:smalivm:jar` | `smalivm/build/libs/smalivm-2.0.0-SNAPSHOT.jar`, without dependencies |
| `:smalivm:fatJar` | `smalivm/build/libs/smalivm-2.0.0-SNAPSHOT-all.jar`, including runtime dependencies |
| `:smalivm:proguard` | Optional optimized `smalivm-2.0.0-SNAPSHOT-proguard.jar`; not part of `build` |
| `jacocoRootReport` | VM and optimizer tests plus aggregate HTML/XML coverage |
| `:smalivm:printSmaliAssemblerClasspath` | Resolved runtime classpath for the ART tooling |

Fat JARs are explicit tasks, not dependencies of `build`. Their output paths are distinct from thin
JARs; no platform-dependent symlink supplies an executable name. Application JAR manifests and
generated distribution launchers supply the `java.base/java.lang` module opening required by host
reflection. External embedding callers must supply it themselves.

Fat JARs unpack the runtime classpath and exclude duplicate entries. Application fat JARs remove
dependency signature files. Every project JAR carries the project `META-INF/LICENSE`,
`META-INF/THIRD_PARTY_NOTICES`, and component-specific `META-INF/licenses/` texts.
Application ZIP/TAR distributions expose these legal files at their top level as well.
Component directories preserve distinct upstream notices even when the original dependency JAR
paths collide. Thin ZIP/TAR distributions also retain dependency JARs separately.
JAR tasks enable ZIP64 because the API 36 framework plus runtime dependencies exceeds ZIP's
65,535-entry limit. JDK 21 reads these archives directly.

The maintained legal bundle describes this release's dependency versions. Dependency updates must
update the matching component texts, copyright notices, and source locations; Maven license labels
alone do not replace upstream notices. Fat-JAR packaging does not merge arbitrary service descriptors.

The optional ProGuard pipeline consumes the distinct SmaliVM fat JAR and uses JMODs from the build JVM.
`runProguard` optimizes JVM code into an intermediate JAR, excluding unchanged framework Smali.
`proguard` packages that output with the Smali using Gradle's ZIP64 writer; ProGuard's direct output
wrapped the entry count for the full resource-heavy bundle. Public APIs, attributes, disabled
obfuscation and the existing optimization policy are preserved. This is not signing or publication approval.

## Framework and Android execution inputs

The framework Smali submodule supplies the selected Android 16 / API 36 corpus from
`android-36/smali/`. `generateFrameworkCatalog` produces catalog resources during
`processResources`, including source hashes and method declarations. Catalog schema 2 records
Android API 36 separately from DEX version 039. Framework parsers derive the opcode table from
the DEX version (Smali API 29), not the device API. Application input/output API selection is unchanged.

`updateReferenceFramework` regenerates the tracked `framework_classes.cfg` and
`framework/android-framework.jar` from that catalog and the selected sources:

```sh
./gradlew :smalivm:updateReferenceFramework
```

It parses one class at a time, builds JVM reference shapes with deterministic entry ordering/times,
and replaces the tracked outputs only after all classes generate. It does not read the previous
class index to determine its inputs. This is a mutating maintenance command, not part of ordinary
`build`; commit its outputs when changing the selected corpus.

The submodule's standalone `make_reflib` generator captures a booted emulator's framework separately.
The tracked API 36 capture retains original JARs/DEX, manifests, image metadata and notices.
`processResources` includes only `android-36/smali/**/*.smali` from the submodule as executable
framework resources; API 25, raw extraction inputs, trial captures, tooling and caches are excluded.
The legal bundle separately includes API 36 provenance, boot/source manifests and original notices.
Generating another capture does not automatically change the selected framework.

The Kotlin engine uses `ReflectionPolicy` for host-call authorization and tracked heap identities
for mutable values. The old `safe_framework_classes.cfg` and `immutable_classes.cfg` lists did not
control this engine and are removed, along with their unused accessors. Active method/class
reflection policies remain unchanged; framework availability is not permission to execute host code.

The ART assembler uses the same resolved Smali dependency and explicit DEX API level as SmaliVM.
It asks Gradle for its classpath each time rather than retaining a second dependency cache. Fresh
runtime comparison remains separate from JVM tests; see `tools/art-runner/` and `tools/emulator/`.

Simplify reads Smali, DEX, and APK inputs. APK output replaces the primary `classes.dex`, preserves
other entry bytes/compression/timestamps/comments and the archive comment, and requires re-signing.
It does not claim multi-DEX optimization or Android application installation.

## CI and release boundary

All four modules use **2.0.0-SNAPSHOT** until the public release is approved. The major version reflects
the incompatible embedding API and JDK 21 requirement; it does not publish the separate commercial product.
Project-owned code is Apache-2.0. Dependencies and vendored source retain their original terms.

GitHub Actions (`.github/workflows/build.yml`) builds/tests on pull requests and pushes to `master`
and `release/**`, using JDK 21 and the framework submodule. Release branches can therefore be
validated on GitHub before landing on `master`, without requiring a pull request. CI builds all
four fat JARs and the optimized ProGuard VM JAR, then uploads aggregate JaCoCo HTML/XML as a
workflow artifact. It needs no external coverage-service credentials. The old
Travis/Coveralls/Coverity hooks are removed; no coverage-trend or external static-analysis upload
is claimed. Local workflow validation is not evidence of a successful hosted run.

The Android framework corpus and derived reference artifacts remain under their upstream terms,
separate from Simplify's Apache license. The API 36 capture records its image fingerprint and
source/tool hashes. The historical API 25 corpus is retained only in the submodule; its original
source-image fingerprint was not recorded. See `THIRD_PARTY_NOTICES` for the license boundary
and capture records. New capture records do not establish the old corpus's exact source image.

Before release, verify a hosted CI run, review the complete public diff and legal bundle, and remove
`-SNAPSHOT` only when tagging the release.
Build tasks do not sign APKs, publish packages, create tags, or push repository history.
